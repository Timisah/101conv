# Product maturity audit and Milestone A map

The October 2026 main branch already has a Go Core, a separate restricted Worker role, PostgreSQL jobs and accounts, React web, engine/profile/repository managers, conversion and compression jobs, preferences, and roles/groups/quotas. Jobs record an execution specification, uploads and results have distinct persistent mounts, and the Worker validates output before registering a result. Compose exposes only the web service on 5656.

| Area | Before this iteration | This iteration | Still needed |
|---|---|---|---|
| First run | Manual Compose variables, token login, no claim flow | Local installer generates secrets; atomic first-account claim and resumable storage review | Portainer secret generation outside the UI; guided trusted converter test on every supported platform |
| Storage | Durable files, no lifecycle view | Separate cleanup policies for unsubmitted uploads, submitted originals, successful results, failed originals, and canceled originals; resumable read-only filesystem scans measure uploads/results/engines, modified-age buckets, per-user totals, and missing/unreferenced references | Temporary-file retention controls, metadata retention, reviewed orphan deletion |
| Jobs/diagnostics | Durable leases, but synthetic running percent | Worker heartbeat and truthful indeterminate progress; low-space rejection | Human-readable per-engine failure taxonomy; batch model |
| Operations | Basic health endpoints | Admin readiness view with Worker heartbeat, lease count, storage, engines and repository status | Alert delivery and measured Worker temp usage |
| Backup | Named volumes and bind, no verified full backup | Stopped-writer backup, checksums, archive verification and isolated restore test | Automated schedules, incremental/config-only backup, migration matrix |

Data dependencies: account/setup/retention/cleanup/heartbeat state is in PostgreSQL; installed engine binaries and repository trust state are in Go data; uploads/results are named volumes. The backup tool freezes Core and Worker writers while dumping PostgreSQL and copying all three file stores. Existing `DATA_PATH`/`GO_DATA_PATH`, Compose service names, and named volumes remain unchanged. New SQL tables are additive and migrations are idempotent.

Security boundaries: the bootstrap passphrase must be random and at least 24 characters for first claim; account creation is serialized by a PostgreSQL row lock. The existing administrator passphrase remains usable after claim for compatibility and must be protected as a full administrator credential. Repository trust does not make executables safe. The Worker still has no network or Docker socket. The documented snap Docker `no-new-privileges` entrypoint failure remains unresolved; the setting is not silently enabled or replaced with a weaker Worker model.

On the cloud test Docker host, `docker run --network none --security-opt no-new-privileges:true --entrypoint /bin/true postgres:17-alpine` succeeded. This does not establish that the previously reported Ubuntu snap Docker host accepts that option. A production Compose change would require a host-specific entrypoint and conversion test first.

New installations keep files indefinitely. Legacy abandoned-upload ages migrate to the matching unsubmitted-upload policy. Cleanup previews bind to the file category, cutoff, counts, recorded bytes, and a short-lived token. File deletion leaves database tombstones and audit events, so history distinguishes expired files from missing ones. Successful originals can be deleted only after a successful job has a registered result that is still present and matches its recorded size. Active and queued jobs are excluded. Cleanup claims and observed byte counts support recovery after a Core crash. The Admin Storage page now exposes each file policy and manual preview/cleanup controls.

Capacity measurements come from Core mounts; PostgreSQL reports the current database's allocated size, while its container filesystem free capacity is not exposed to Core. Worker `/work` is a 1 GiB tmpfs; live usage remains unavailable to Core. PostgreSQL-recorded upload/result sizes remain estimates relative to files on disk. The administrator can run a resumable, bounded, read-only scan of uploads, results, and managed engines; it records measured bytes, modification-age buckets, reference discrepancies and sample relative paths, and measures uploaded/results per owner. It also reports queued/running input bytes separately, without presenting them as scratch/output forecasts. A scan can observe concurrent changes and is not a transactional filesystem snapshot. It never deletes orphan files. Job metadata has no age-based retention setting. Temporary Worker files are ephemeral scratch and are removed with each attempt/container restart; they have no separate configurable retention policy. Backup and retention have no access to arbitrary host paths through the browser.

The backup manifest now records whether Compose and an environment file were included, and records that Portainer UI variables cannot be exported by the script. The isolated restore checker verifies checksums, archives, PostgreSQL restore, job/upload metadata references, and live file references while ignoring expired tombstones. It still does not boot Core/Worker or run a conversion. A production restore should first be rehearsed in an isolated deployment.

Still outstanding in Milestone A: job-metadata and temporary-file retention controls, reviewed orphan deletion, application-level restore with a real conversion, durable session and administrator credential lifecycle, and automated backup scheduling. Milestone B is durable batches, marketplace details, and profile smoke tests. Watch folders and scheduling remain later work.
