# Compression workflow

Compression is a separate user workflow and a durable job mode. `POST /api/v1/compressions` uses the same authenticated upload, job ownership, cancellation, result, and quota boundaries as conversion. A request selects an installed profile, a supported output extension, and profile-declared option values; clients cannot submit executable paths or argument arrays.

## Profile contract

Repository profiles declare a `type`: `conversion` or `compression`. Conversion profiles cannot define compression controls, and the API rejects using a profile in the other workflow. A compression profile exposes a `compression` block containing typed options; numeric options have server-enforced bounds and select options must match the declared choices. A compression rule uses one `{compression.args}` marker in its argv list, where the Worker inserts its validated arguments. This explicit insertion point preserves paired output flags such as `--output {target}`. Literal profile tokens are argv elements, and `{option:key}` references are expanded only after validating the value against the profile schema. Older installed definitions without a `type` retain their previous behavior for compatibility.

For media size targets, the profile marks a numeric option with `targetSizeMb`, declares an installed `probeExecutable`, and supplies bounded bitrate settings. Its compression arguments can use `{compression.videoKbps}`, `{compression.audioKbps}`, and `{compression.bufferKbps}`. The Worker runs one bounded typed JSON media probe against the private input, derives an average bitrate from duration and target size, reserves 10% for muxing overhead, then passes the resulting arguments directly to the declared converter without a shell. It validates the final artifact against the requested size and rejects output that exceeds the target. Profiles can explicitly declare stream selection, safe metadata/chapter preservation, and HDR policies; the Worker maps only those allowlisted policies and checks output equivalence for every selected video stream, including resolution, HDR transfer/primaries/matrix/range, bit depth, static HDR side data, and configured dynamic HDR payload behavior. A downgrade fails the job rather than silently publishing an unapproved stream, metadata, SDR, or resized output.

Only compression profiles appear in the Compress workflow, and only conversion profiles appear in Convert. The UI defaults to the source extension when the selected compression profile supports that pair. When it does not, the user can explicitly choose another output format, combining compression and format change in one compression job. These are separate profiles, and dependency resolution reuses their common engine installation.

## Current catalog support and upgrade

The catalog now publishes separate FFmpeg conversion/compression profiles and separate JPEG XL conversion/compression profiles. The FFmpeg compressor adds target-size controls for its supported audio and video formats and requires an FFmpeg engine with `media.probe` and `ffprobe`. The JPEG XL compressor exposes bounded quality while encoding JPEG, PNG, APNG, or GIF inputs to JXL; it does not support same-extension recompression. Each profile pair references one shared engine package.

When an existing installation updates profiles, the dependency resolver installs the compatible engine package only if needed; both profiles then reference that shared installation. Existing engine files and job history are preserved. Old profile installations without an explicit type remain usable until administrators install separate typed profiles. Community authors publish one profile for each workflow; engine downloads are not duplicated.

## Limits

Target size is estimated from duration and average bitrate, not guaranteed by the encoder. 101conv returns no artifact above the requested size; it currently reports that job as failed instead of automatically retrying at lower bitrates. Codec/container overhead and minimum viable bitrates can therefore make a very small target unattainable. FFmpeg provides target-size audio/video compression. JPEG XL provides a quality control rather than a target-size guarantee; other image profiles remain conversion-only until they declare compression rules and their encoder semantics are validated.
